# CLI Reference

This is the authoritative command surface for the `pio-agent` CLI (also
installed as `platformio-mcp`). It is generated by running:

```bash
npm run build && node build/cli.js --help
```

If this drifts from what `--help` actually prints, trust `--help`.

`--json` prints machine-readable output on stdout; without it, output is
formatted for a human. Always pass `--json` when you intend to parse the
result programmatically. `--approve` authorizes the current action when a
policy requires it — only pass it when the user has explicitly approved that
exact action.

## Worked examples

### Build

```bash
pio-agent build --project-dir ./firmware --environment esp32dev --json
```

For a large project, add `--background` so the command returns immediately:

```bash
pio-agent build --project-dir ./firmware --environment esp32dev --background --json
# => { "status": "running", "taskId": "...", "logPaths": ["..."] }
pio-agent task-status <task-id> --json
```

Poll `task-status` until `status` is `completed` or `failed`; do not assume
completion just because the shell prompt returned.

### Flash with a resolved target

Never guess a port or environment for a write operation. Resolve first, then
flash with the exact values `target-resolve` returned:

```bash
pio-agent target-resolve --project-dir ./firmware --environment esp32dev --json
# => { "success": true, "status": "resolved", "environment": "esp32dev",
#      "port": "/dev/cu.usbserial-1420", "binding": { ... "digest": "..." } }

pio-agent flash --project-dir ./firmware --environment esp32dev \
  --port /dev/cu.usbserial-1420 --json
```

Stop and report to the user if `target-resolve` comes back with
`status: "ambiguous"` or `"invalid_config"`, or multiple candidates — do not
pick a port yourself.

### Bounded monitor with expectations

Wait for a specific boot marker instead of reading serial output forever:

```bash
pio-agent monitor --project-dir ./firmware --port /dev/cu.usbserial-1420 \
  --expect "BOOT_OK" --timeout 15 --json
```

This blocks until `BOOT_OK` appears or the 15-second timeout elapses, then
returns whether the expectation matched. For a fire-and-forget monitor that
should keep spooling to disk in the background, add `--background` instead
of `--expect`, and read it later with:

```bash
pio-agent logs query --port /dev/cu.usbserial-1420 --lines 100 --json
```

### Library install

```bash
pio-agent lib install "ArduinoJson" --project-dir ./firmware --version 7.1.0 --json
```

Always pin `--version` for reproducible builds. Verify with:

```bash
pio-agent lib list --project-dir ./firmware --json
```

### Recovering from `PORT_BUSY`

```bash
pio-agent flash --project-dir ./firmware --port /dev/cu.usbserial-1420 --json
# => { "success": false, "errorType": "PortBusy", "safeToAutoRetry": false,
#      "summary": "Port /dev/cu.usbserial-1420 is already claimed by PID 4821 (upload) in /Users/alice/firmware." }
```

Do not retry in a loop — `safeToAutoRetry` is `false` for a reason. Instead:

```bash
pio-agent lock status --port /dev/cu.usbserial-1420 --json
```

Report the holding PID and workspace to the user. Only if the user confirms
that process is finished, clear the claim:

```bash
pio-agent port release --port /dev/cu.usbserial-1420 --force --json
```

Without `--force`, `port release` refuses to clear a claim held by a live
process — that refusal is expected behavior, not a bug.
